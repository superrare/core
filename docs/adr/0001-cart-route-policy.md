# Route cart payments through validated intermediate custody

The cart accepts platform-signed, order-wide Universal Router command plans, but validates every command, flag, nested action, recipient, and route shape through a dedicated `CartRoutePolicy` derived from the proven Liquid Router policy. Swap outputs return to the cart for aggregate balance-delta validation before payout. Both unused input and output above signed line obligations are favorable execution variance belonging to the configured protocol recipient under the signed fixed quote. The policy enforces route endpoints against the signed payment and settlement-currency basket; intermediate route-token selection is backend-owned and covered by the platform signature. Cart balance surveillance covers only those signed input and output currencies.

The policy admits explicitly decoded V2/V3 exact-input and exact-output swap shapes and narrowly decoded V4 plans containing one swap plus `SETTLE_ALL` and `TAKE_ALL`. It requires every operation to succeed, restores signed Cart currency balances to their pre-transaction baselines, rejects any increase in those currencies at the Universal Router, verifies temporary router/Permit2 allowances are zero, and supports exact-input and exact-output routes only where their complete postconditions are enforced. Universal Router pre-existing balances may be consumed because they are publicly extractable, but the Purchase Order may not leave new payment or settlement funds there. Universal Router NFT-marketplace, wrap/unwrap, sweep, arbitrary V4 actions, and other unspecified commands are explicitly out of scope. The router address is configured once with no runtime setter; new router versions, commands, or nested actions require a code change and review rather than an administrative allowlist update.

The policy is a stateless contract of its own, named by a cart implementation immutable rather than by proxy storage, so it keeps the same "audited upgrade, not administrative setter" property while staying outside the cart's EIP-170 budget. Calling it externally also gives the cart the `try`/`catch` boundary it needs to report which Order Line a rejected route belongs to.
